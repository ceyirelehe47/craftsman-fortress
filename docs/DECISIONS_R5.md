# R5 决策记录

## R5-01 · 建筑构件是独立权威层

薄墙、楼板、门窗、楼梯、屋顶、柱梁不注册为 `BlockId`，也不写入 Chunk。`BuildingStore` 保存稳定构件 ID、稳定类型、整数锚点和四向旋转；ECS Entity 与程序化 Mesh 只是可重建表现。

## R5-02 · 薄构件使用规范化槽位

- 楼板与平屋顶占用水平单元平面；
- 墙、门洞与窗占用同一种规范化竖直边槽；
- 柱占用网格点；
- 梁占用水平边；
- 楼梯占用离散 1×3、上升 3m 的通行体积。

反向描述同一条边时必须规范化到同一槽，不能因为锚点或朝向相反而重复放置。

## R5-03 · 首轮层高固定为 3m

R5 的墙、门窗、柱和楼梯使用 `STORY_HEIGHT=3`。这是当前建筑玩法契约，不代表未来所有内容只能使用单一层高；若以后支持其它层高，应新增稳定类型或版本化语义，不得静默改变已有类型。

## R5-04 · 支撑关系是确定性整体约束

放置、移动、旋转和删除都先在候选快照上重算整个建筑集合。失败不得修改 ID、位置、索引、`next_id` 或 revision。

- 地面楼板可由下方实体地形支撑；
- 抬高楼板和屋顶的四角必须有墙、门窗、柱或梁提供的结构端点；
- 墙、门窗和柱必须由地形或楼板平台支撑；
- 梁两端必须落在墙或柱顶端；
- 楼梯低端和高端必须精确连接楼板。

R5 不实现载荷、材料强度、坍塌动画或物理破坏。

## R5-05 · 三个权威层互相约束但不互相吞并

- 地形编辑不得破坏建筑支撑或填充建筑所需空间；
- 建筑不得穿过独立对象；
- 新放置或移动的独立对象不得穿过建筑薄面或楼梯体积；
- 地面楼板可与站在其上方、仍由地形支撑的对象共存。

抬高楼板作为对象支撑与居民导航属于 R6，不在 R5 修改 `CFOBJ001` 的加载语义。

## R5-06 · 程序化视觉先验证模块语义

R5 使用 Bevy 基础 Mesh 生成楼板、墙、门框、窗框、楼梯、屋顶、柱和梁，不新增第三方素材依赖。视觉加载顺序、Entity 分配和材质句柄均不进入语义哈希或永久存档。

## R5-07 · `CFBLD001` 与既有格式分层

- 地形继续使用冻结的 `CFSAVE02`；
- 独立对象继续使用冻结的 `CFOBJ001`；
- 建筑构件使用新伴随格式 `CFBLD001`。

R5 不修改 `src/persistence.rs`，也不改变既有对象记录布局。

## R5-08 · 建筑槽绑定地形与对象语义

每个 `CFBLD001` 槽同时保存 terrain semantic hash 和 object semantic hash。只有两者都与当前已加载权威层一致，建筑槽才可物化。这避免同一地形下不同对象状态误配旧建筑状态。

## R5-09 · 建筑预写、对象预写、地形后提交

F5 保存顺序为：

1. 物化磁盘上的旧耐久地形和与其配对的对象层；
2. 预写新建筑槽，同时保护与旧地形+旧对象匹配的建筑槽；
3. 预写新对象槽，同时保护与旧地形匹配的对象槽；
4. 最后原子提交地形。

任一步中断时，旧地形仍能选择旧对象和旧建筑；地形提交成功后，新三层状态才一起生效。

## R5-10 · R4 历史存档兼容

没有 `.buildings.slot0/.slot1` 的 R4 或更早存档加载为空建筑层。存在建筑槽但没有任何完整匹配槽时必须明确报错，不得静默丢弃建筑。

## R5-11 · 验收证据不递归套娃

R5 完整验收先运行 R4 全回归，但最终证据只保留展开后的历史证据；删除子轮 ZIP 与旧子级校验清单，再由 R5 根级 `SHA256SUMS.txt` 覆盖全部保留文件。不得通过提高泄漏守卫深度上限来容纳无限嵌套。

## R5-12 · 明确不扩项

R5 不实现导航图、居民、工作循环、自动寻路、建筑流送、LOD、无限世界、浮动原点、结构坍塌或完整建造 UI。这些继续按既定路线进入 R6 及以后阶段。

## R5-13 · 实现期等价修正（应用参考补丁后）

参考补丁在制包环境无法编译运行，实现方应用后做了以下等价修正，均不降低 R5 验收门槛：

1. **rustfmt 解析歧义**（`src/buildings.rs`）：4 处 `edge.start.z as f32 < max.z`
   被 rustfmt 解析为泛型实参起始，阻断 `cargo fmt`。按编译器建议加括号
   `(edge.start.z as f32) < max.z`，语义不变。
2. **测试世界尺寸与 Chunk 覆盖不一致**（`src/buildings.rs`、
   `src/building_persistence.rs`）：两个 `flat_world` 使用 `WorldSize::new(40, 32, 40)`，
   40 不是 `CHUNK_SIZE=16` 的倍数——`contains()` 认为体素界内而 `chunks()` 整除
   得 2×2×2 只覆盖 32 个体素，`set_voxel` 在 x/z∈[32,40) 触发 `slot_index().unwrap()`
   panic，13 个 R5 单测失败。改为 `48×32×48`（16 倍数、覆盖全部测试锚点），
   与既有 `objects.rs`/`building_runtime.rs` 测试 helper 的取值惯例一致。
3. **键盘会话单测的按键顺序**（`src/building_runtime.rs`）：
   参考补丁测试按 H→L→J 顺序期望移动后 `yaw_quarters=1`，但进入移动（L）会把
   UI 朝向恢复为被移动构件当前值——这与 R4 对象层 M 键语义完全同构
   （`object_runtime.rs` KeyM 同样恢复 `record.yaw_quarters`），属于正确的既有
   交互契约。测试顺序改为 L→H→J（进入移动后再调整朝向并提交），验证同一
   行为而不改变实现语义。
4. **headless watchdog 证据对齐 R4**（`scripts/r5_headless_checks.sh`）：参考补丁
   版超时时仅向 stderr tail 日志且把日志滞留 `*.tmp`。改为 R4 同款模式：日志写
   mktemp 临时目录，超时落 `$OUT/watchdog.txt`（含 tail 100 行），正常结束后
   `cp` 为 `app_stdout.log`。提升失败诊断能力，不改变任何通过门槛。
5. **F03 场景缺陷**（`examples/r5_building_roundtrip.rs`）：参考补丁在闭合
   围栏（墙×2/门/窗围合上层楼板四角）上删单边墙，四角仍有冗余支撑，
   `remove` 合法成功，`is_err()` 断言永假。改为删除柱 (10,21,4)：其顶端是
   梁 (10,24,4) 端点的唯一支撑，删除必然连带梁失去支撑整体失败——这才是
   "删除必要支撑时整体失败"的语义；断言额外增加被删构件仍存在。
6. **中断恢复场景自相矛盾**（同文件）：参考补丁先把 (30,21,30) 编辑为
   Stone，再在 (28,21,28) 放 campfire——campfire footprint 为 3×3
   （[28,31)），必然撞上刚写入的 Stone。编辑点挪到 (20,21,20)，远离两处
   对象与楼板，"新地形哈希 != 旧耐久地形"的语义不变（后续断言只比较
   语义哈希，无坐标引用）。
7. **视觉实验室截图时机与构图**（`examples/r5_building_lab.rs`）：参考补丁
   首拍 1.0s 在首帧管线（窗口创建+着色器编译）完成前触发，第一张截到
   清屏色（单色统计被 `validate_png` 拒绝）；全部拍摄点推迟 1.5s、间隔
   不变。首拍同时从 28m 拉近到约 16m 正对构件条带——远景全景天空占比
   过大使 stddev 跌破 8.0 阈值。构图参数是程序化视觉表现，不进入语义
   哈希；`validate_png` 统计门槛本身未放宽。

## R5-14 · F5 保存前 durable 地形读取的失败语义收紧

R4 基线在保存前读取磁盘旧耐久地形失败（`load_latest(...).ok()`）时降级为
"无保护继续保存"。R5 参考实现改为：磁盘存在地形槽但两槽均无效时阻塞保存
（"Save blocked: durable terrain invalid"）。这是有意收紧——三层提交顺序中，
旧配对保护依赖旧耐久地形的正确物化，静默降级会让旧对象/旧建筑槽失去配对
基准。该行为变化来自参考补丁，实现方审查后判定为与 R5-09 的原子性承诺
一致并保留。
