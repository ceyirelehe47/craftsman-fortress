# R2 决策记录：可修改世界与存档底座

## R2-01 · 修改覆盖层而非全世界快照

Seed、世界尺寸和生成器修订决定基础世界。存档只记录最终值不同于基础世界的体素坐标与方块；恢复基础值时覆盖项自动删除。这样存档大小与玩家修改量相关，而不是与整张三维地图体积相关。

## R2-02 · 语义哈希

R1 的 `world_hash()` 继续用于验证 Chunk palette 与索引的确定性表示。R2 新增 `semantic_hash()`，按固定坐标顺序混合解码后的 BlockId，不受 palette 插入顺序影响。存档的基础哈希与最终哈希均使用语义哈希。

## R2-03 · 双槽原子协议

不依赖跨平台“覆盖式 rename”。逻辑路径轮换 `.slot0` / `.slot1`：写新状态时始终保留当前最新有效槽，目标槽先腾空，再由同目录临时文件原子重命名。加载分别校验两个槽并选择 generation 最大的有效槽。

## R2-04 · 安全编辑边界

- 基岩不可删除或替换；
- 玩家不可放置 Bedrock；
- `H-1` 顶层必须保持空气，以保留 R1.1 的相机恢复安全层；
- 本轮放置材料固定为 Stone；
- 不做背包、材料选择、挖掘耗时、工具耐久或建造规则。

## R2-05 · 启动加载而非运行时热重载

本轮通过 `--load PATH` 启动加载。F5 负责保存；不实现 F9 热重载，避免在 Mesh 全量替换期间向玩家展示新旧世界混合帧。后续需要热重载时，应增加专用加载状态与原子 Mesh 交换。

## R2-06 · 验收分层

`scripts/r2_acceptance.sh` 必须先完整重跑 R1 图形验收，再运行 R2 头部往返测试。实现方与隔离 Reviewer 均从全新克隆执行，用户不参与操作或判断。

## R2.1-01 · 完整有效槽（2026-09-14）

R2 将“通过二进制解码”误当成“有效槽”，导致高 generation 槽在基础或最终语义哈希失败时阻断旧槽回退。R2.1 将槽位有效性定义为完整物化成功：解码、基础生成、基础哈希、覆盖层应用与最终哈希全部通过。加载和保存侧共用这一标准。

## R2.1-02 · generation 与资源上限

generation 使用 `checked_add`，溢出即拒绝保存。解码最多接受 1,000,000 条记录，记录必须严格按坐标递增；文件长度和 edit_count 在分配前验证。

## R2.1-03 · 验收对齐

R2 机器报告曾把 B05–B10 编号错位且缺少 B09–B12。R2.1 报告固定输出 B01–B12；新增主程序损坏加载退出码 3 的进程级测试，并给无窗口程序增加独立 watchdog。第三方素材仍后置到 R3。

## R2.1-04 · 对参考补丁的脚本修正（2026-09-14）

参考实现的 `scripts/r2_headless_checks.sh` 存在两处环境缺陷，落地时修正：其一，脚本只构建往返 example、不构建主程序二进制，CI 单独运行该脚本时损坏启动测试会因缺少可执行文件而失败，现补上 `cargo build --release --bin craftsman_fortress`；其二，脚本原先把被测程序日志直接重定向进证据目录，而往返程序自带“输出目录必须为空”的防污染守卫，日志文件会先于程序创建并导致必然失败，现改为先写入临时目录、进程结束后拷入证据目录（超时与失败路径同样保留日志）。两处修正均不涉及存档协议语义，已在本机验证：正常路径 PASS，`R2_HEADLESS_WATCHDOG_SEC=0` 时以 124 退出并留下 `headless_watchdog.txt`。
